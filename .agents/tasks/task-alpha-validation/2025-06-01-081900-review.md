# Multi-dimensional alpha validation scoring framework

An `AlphaValidator` class evaluates backtested strategies across 8 orthogonal dimensions (return ability, risk-adjusted performance, transaction cost, drawdown risk, efficiency, independence, coverage, robustness) and produces a weighted composite score with per-dimension pass/fail. The design decomposes validation into stateless evaluator classes, each computing domain-specific metrics and mapping them onto a 0-100 scale, then the validator orchestrates them and folds in optional benchmark/existing-alpha context. The module integrates with the existing `BacktestResult` dataclass and exports through the package's top-level `__init__`.

Watch for: profit_factor reports 0.0 instead of infinity when there are no losses, creating a false penalty for perfect strategies (confirmed); the `ValidationConfig` thresholds don't actually gate individual dimension scoring since evaluators use hardcoded scaling constants (confirmed); `IndependenceEvaluator` silently produces a misleading `factor_correlations` metric that's just `abs(corr_market)` rather than multi-factor analysis (confirmed); bootstrap in `RobustnessEvaluator` runs 1000 iterations on every call with no opt-out, which will be expensive on large return series (likely).

## High-level view

The validator is a thin orchestrator: it unpacks `BacktestResult.returns` and `.positions`, fans them out to 8 evaluator instances, collects `DimensionResult` objects, and computes a weighted average.

Scoring within each evaluator uses hardcoded linear mappings (e.g. "Sharpe 0=0, 2.0=100") that are disconnected from `ValidationConfig`. The config controls only the overall pass/fail threshold and dimension weights, not the internal scoring curves. Changing `min_sharpe` in the config doesn't change the score a strategy receives on the risk-adjusted dimension.

The independence evaluator claims factor correlation analysis but actually only computes correlation with the benchmark. The "factor_correlations" metric is `abs(corr_market)`, not a multi-factor decomposition.

Transaction cost scoring penalizes turnover linearly but `estimated_implementation_shortfall`, `capacity_score`, and `market_impact_score` are all linear transforms of `annual_turnover` with no volume or spread awareness — three metrics carrying the same information.

The OOS/IS ratio in the robustness evaluator is sign-blind: a strategy with negative in-sample Sharpe and positive out-of-sample Sharpe gets a negative ratio, which the scoring formula maximally penalizes as "unstable."

4. **Bootstrap cost on large series** — 1000-iteration bootstrap with full-length resampling on every `validate()` call. For 10-year daily data (2520 points), this is ~2.5M random draws per call with no caching or opt-out. Add a `skip_bootstrap` config option or reduce default iterations for large n. (likely)
5. **Implementation shortfall is a constant multiplier** — `annual_turnover * 0.001` ignores volume, spread, and market cap. The metric exists but has no informational value beyond what `annual_turnover` already provides. Document it as a placeholder or remove. (confirmed)
6. **OOS/IS ratio sign-blind** — If in-sample Sharpe is negative and out-of-sample Sharpe is positive, the ratio is negative, which gets penalized by the `abs(1.0 - oos_is_ratio)` formula. A strategy that improves out-of-sample is scored as unstable. (confirmed)
7. **No input validation on BacktestResult** — If `positions` is empty or `returns` has NaN values, several evaluators will silently produce misleading scores rather than raising. (likely)

## Profit factor and win/loss edge cases

The `ReturnAbilityEvaluator` guards against division-by-zero in profit factor by checking `gross_losses > 0`, but when a strategy has exclusively winning periods, it returns `profit_factor = 0.0`. A strategy that never loses receives the minimum profit-factor score. The same issue appears in `avg_win_loss_ratio`. The scoring formula `pf_score = (profit_factor - 1.0) / 1.0 * 100.0` clips this to 0, penalizing perfect strategies on 30% of the return ability score.

```python
profit_factor = (
    gross_profits / gross_losses if gross_losses > 0 else 0.0  # should be inf or capped high
)
```

The test `test_all_positive_returns` verifies `hit_rate == 1.0` but doesn't assert that the score reflects the perfect-win scenario appropriately.

## Config-to-evaluator gap

`ValidationConfig` defines `min_sharpe=0.5`, `min_sortino=0.7`, `max_drawdown_threshold=-0.30`, `max_annual_turnover=20.0`, `min_hit_rate=0.45`, `min_profit_factor=1.0`. None are passed into or read by any evaluator. The evaluators use hardcoded linear ramps:

- Sharpe scoring: `sharpe / 2.0 * 100.0`
- Drawdown scoring: `(abs(mdd) - 0.50) / (0.05 - 0.50) * 100.0`
- Turnover scoring: `(50.0 - annual_turnover) / 45.0 * 100.0`

A user who sets `min_sharpe=1.5` expecting stricter scoring of the risk-adjusted dimension gets no behavioral change. The tests `test_strict_vs_lenient_config` confirm this: both configs produce the same `overall_score`, only `overall_passed` differs. The config fields create a false API promise.

## Independence evaluator's scope gap

```python
factor_corrs["market"] = corr_market
metrics["factor_correlations"] = float(abs(corr_market))  # Not multi-factor
```

The factor decomposition (size, value, momentum proxies mentioned in the feature spec) is absent. When `existing_alpha_returns` is provided, pairwise correlations are computed correctly and `marginal_contribution` works as expected. But the `factor_correlations` metric key will mislead any automated system consuming the report dict downstream expecting Fama-French-style exposures.

## OOS/IS ratio scoring asymmetry

The robustness score uses `(1.0 - abs(1.0 - oos_is_ratio)) * 100.0`. If `sharpe_1` is negative (bad in-sample) and `sharpe_2` is positive (good out-of-sample), the ratio is negative: `positive / negative = negative`. This produces `abs(1.0 - (-x))` = `1 + x`, exceeding 1.0, and the score clips to 0. A strategy that performs poorly in the first half but recovers in the second half is maximally penalized on robustness. The fix is to compare absolute Sharpe magnitudes or handle sign flips explicitly.

## Transaction cost model redundancy

The `estimated_implementation_shortfall = annual_turnover * 0.001` applies a flat 10bp cost assumption. `capacity_score = 100 - turnover * 2.0` and `market_impact_score = 100 - turnover * 1.5`. These three metrics are linear transforms of the same input. Without volume data (which the evaluator's signature doesn't accept), they occupy metric real estate without adding signal beyond what `annual_turnover` already provides.

## Test gaps

Not tested: behavior when `returns` contains NaN values; the OOS/IS sign inversion on strategies with negative in-sample Sharpe; profit_factor scoring when all returns are positive (the test checks hit_rate but not the score penalty); whether `to_dict()` produces valid JSON (metrics can contain inf/nan from division edge cases, which are not JSON-serializable).
